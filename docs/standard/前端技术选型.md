# 幻觉 IP 官方网站 — 前端技术选型

> 创建日期: 2026-07-28
> 版本: v1.0
> 状态: 已确定，待实施

---

## 一、背景

### 1.1 项目概述

「幻觉」是以长篇连载小说为骨架、AI 原生音乐/MV 为血肉、家族族谱为经脉的跨媒介独立自媒体 IP。本项目需构建其官方网站，聚合以下内容板块：

| 板块 | 数据来源 | 说明 |
|------|----------|------|
| 小说 | `xujie-writer-agent` → `data/XujieWriter-data/` | 《幻觉》连载章节（Markdown） |
| 音乐 | `lemong-agent` → `data/Lemong-data/` | AI 原创歌曲（MP3 + 歌词 + 创作背景） |
| MV | `erhu-agent` → `data/Erhu-data/` | 数字人歌手 MV（MP4 + 图片素材） |
| 族谱 | `zhupu-manager-agent` → `data/Zhupu-data/` | 小说角色家族族谱（JSON） |
| 社区 | — | 读者互动、评论（阶段二） |

### 1.2 核心约束

| 约束 | 详情 |
|------|------|
| **Agent 工作模式** | Agent 在 WebIDE 中手动运行，产出物保存到本项目的 `data/` 目录 |
| **服务器** | 阿里云 ECS，**1.8G 内存**，40G 磁盘，Alibaba Cloud Linux 8 |
| **域名** | `[已配置域名]`（已有 Nginx + SSL） |
| **内容更新频率** | 低频，手动触发（Agent 运行 → `git push` → 部署） |
| **内容性质** | 90% 纯内容展示（章节正文、歌词、MV 列表），10% 交互（族谱树、播放器） |

### 1.3 关键决策因素

1. **内存极其紧张** — 1.8G 内存不能常驻 Node.js 运行时
2. **内容为主** — 大多数页面是纯阅读/浏览体验，不需要 SPA
3. **更新低频** — 不需要 ISR/SSR 的实时渲染能力
4. **无后端依赖** — 数据源是本地文件系统，不需要数据库

## 二、方案对比

### 2.1 候选方案

| 方案 | 类型 | 运行时 | 输出 |
|------|------|--------|------|
| **Astro** | SSG（静态站点生成） | 构建时 Node.js | 纯 HTML/CSS/JS |
| Next.js (SSG) | React 框架 | 可选 Node 运行时 | HTML + JS Bundle |
| Nuxt (SSG) | Vue 框架 | 可选 Node 运行时 | HTML + JS Bundle |
| Hugo / 11ty | 纯 SSG | 构建时 Go/Node | 纯 HTML/CSS/JS |

### 2.2 关键维度对比

| 维度 | Astro | Next.js | Nuxt | Hugo |
|------|-------|---------|------|------|
| **服务器运行时内存** | ≈0（纯静态文件） | 500MB+（Node 进程） | 500MB+（Node 进程） | ≈0 |
| **构建时读取本地 data/** | ✅ 原生 `import.meta.glob` | ✅ `fs.readFileSync` | ✅ `fs.readFileSync` | ✅ 模板函数 |
| **Markdown/MDX 支持** | ✅ Content Collections | ✅ | ✅ | ✅ |
| **交互组件方案** | Islands 架构（按需 JS） | 全量 React | 全量 Vue | 需额外引入 |
| **产物体积** | KB 级 HTML | MB 级 JS Bundle | MB 级 JS Bundle | KB 级 HTML |
| **CSS 方案** | 任意（推荐 Tailwind） | 任意 | 任意 | 任意 |
| **学习曲线** | 低（类 JSX，Web 标准） | 中 | 中 | 低 |
| **生态成熟度** | 快速增长，1.0 稳定 | 非常成熟 | 成熟 | 成熟 |
| **图片/视频优化** | 内置 `astro:assets` | `next/image` | `@nuxt/image` | 需额外处理 |

### 2.3 排除法分析

**排除 Next.js / Nuxt**（SSG 模式也不行）：
- 即便是纯静态导出模式（`output: 'export'`），构建产物体积仍然较大
- 交互组件（族谱树、播放器）需要引入 React/Vue 运行时 → 每个页面都携带框架代码
- 虽然可以用纯 SSG 方式部署（`next build && next export`），但项目结构是为 SSR/ISR 设计的，用纯 SSG 是大材小用

**排除 Hugo / 11ty**：
- 能胜任纯内容展示，但族谱树可视化、音乐播放器等交互组件的开发体验差
- 模板语法受限，不适合复杂的交互式页面

**选择 Astro**：
- 核心哲学匹配：Content-first, JavaScript as needed
- 90% 页面零 JS → 极致性能、极小体积
- 10% 交互组件按需加载（Islands）→ 不污染其他页面
- Markdown 是一等公民 → 小说章节直接写 `.md` 或 `.mdx`
- 构建时读取 `data/` 目录的能力与 Agent 工作流天然契合

## 三、最终选型

### 3.1 技术栈

| 层级 | 选型 | 用途 |
|------|------|------|
| **框架** | **Astro** (v4+) | 全站 SSG 框架 |
| **CSS** | **Tailwind CSS** (v4) | 原子化 CSS，内容站点开发效率高 |
| **族谱可视化** | **D3.js** | 交互式族谱树（SVG 渲染），灵活可控 |
| **内容管理** | Astro Content Collections | 小说章节等 Markdown 内容的结构化管理 |
| **数据读取** | `import.meta.glob` + `fs` | 构建时扫描 `data/` 目录，生成静态页面 |
| **部署** | Nginx 静态文件 serve | 零运行时，零内存开销 |
| **CI/CD** | GitHub Actions | `git push` → 服务器 `git pull && npm run build` |

### 3.2 页面架构

```
全站 = 静态 HTML 页面
       │
       ├── 纯内容页（零 JS）:
       │   ├── 小说章节阅读
       │   ├── 歌词展示
       │   ├── MV 作品列表
       │   └── 家族列表
       │
       └── 交互 Islands（按需加载 JS）:
           ├── <FamilyTree />     — D3.js 族谱树
           ├── <AudioPlayer />    — 音乐播放器
           ├── <VideoPlayer />    — MV 播放器
           └── <CommentWidget />  — 社区评论（阶段二，Giscus）
```

**Islands 架构的核心优势**：族谱树页面的 D3.js 只在访问该页面时加载，不影响小说阅读页的性能和体积。

## 四、数据分发架构

### 4.1 分发链路

```
┌─────────────────────────────────────────────────┐
│  WebIDE (/workspace)                            │
│                                                 │
│  Agent 手动运行 → 产出到 data/                   │
│       │                                         │
│       │ git add data/ && git commit && git push  │
│       ▼                                         │
│  GitHub: xplan2026/mirage-studio                 │
│  (代码 + data/ 内容的单一信任源)                  │
│       │                                         │
│       │ 服务器端: git pull origin main           │
│       ▼                                         │
│  Server: [服务器 IP]                           │
│  ┌─────────────────────────────────┐           │
│  │  npm run build                  │           │
│  │  ├── 扫描 data/                 │           │
│  │  │   ├── XujieWriter-data/ → 生成小说页      │
│  │  │   ├── Lemong-data/      → 生成音乐页      │
│  │  │   ├── Erhu-data/        → 生成 MV 页      │
│  │  │   └── Zhupu-data/       → 生成族谱页      │
│  │  ├── 媒体文件复制到 dist/assets/media/       │
│  │  └── 输出 dist/ (纯静态文件)                  │
│  ├─────────────────────────────────┤           │
│  │  Nginx → serve dist/            │           │
│  └─────────────────────────────────┘           │
└─────────────────────────────────────────────────┘
```

### 4.2 关键设计决策

**为什么用 GitHub 做中间桥？**
- WebIDE 和服务器之间不需要直接网络连接
- GitHub 是 `data/` 和源代码的单一信任源（SSOT）
- 支持版本回溯 — 每次内容更新都可追溯
- 便于 CI/CD — GitHub Actions 可以自动触发部署

**为什么不用 API/数据库？**
- 内容更新频率极低（Agent 手动运行），不需要实时性
- 额外的 API 层增加运维负担（需要进程管理、数据库备份等）
- 静态构建足够满足需求，保持架构简单

**媒体文件（MP3/MP4/图片）如何处理？**
- 阶段一：构建时复制到 `dist/assets/media/`，Nginx 直出
  - 优势：零额外配置，立即可用
  - 风险：磁盘空间（40G），MP4 文件较大
- 阶段二（需要时）：迁移到 Cloudflare R2（免费 10GB，超出按量付费）
  - 构建时上传，前端通过 CDN URL 引用
  - 释放服务器磁盘压力

### 4.3 构建时数据读取

Astro 在 `astro.config.mjs` 中配置 `data/` 路径别名，在页面的 `getStaticPaths()` 中读取：

```typescript
// src/pages/music/[...slug].astro
import { getSongs } from '../../lib/data';

export async function getStaticPaths() {
  const songs = getSongs(); // 读取 data/Lemong-data/ → 产物列表
  return songs.map(song => ({
    params: { slug: song.id },
    props: { song }
  }));
}
```

所有内容在构建时一次性编译为静态 HTML，不依赖任何运行时数据源。

## 五、社区功能（阶段二）

社区板块（评论、互动）在阶段二引入，**不破坏静态架构**：

| 功能 | 方案 | 说明 |
|------|------|------|
| 章节评论 | Giscus（GitHub Discussions） | 免费，基于 GitHub OAuth，无后端 |
| MV/歌曲评论 | Giscus | 同上，按页面路径区分 discussion |
| 读者订阅 | 第三方服务 | Mailchimp / ConvertKit 嵌入表单 |
| 动态通知 | Cloudflare Workers | 轻量级 API，必要时引入 |

选择 Giscus 的理由：
- 零服务器成本（数据存在 GitHub Discussions）
- 无需自建用户系统
- Astro 可以无缝嵌入（一个 `<script>` 标签）
- 评论审核通过 GitHub 完成

## 六、总结

```
选型结论: Astro + Tailwind CSS + D3.js
部署方式: 纯静态 SSG → Nginx serve
数据流:   Agent 产出 data/ → git push → GitHub → git pull → npm run build → Nginx
设计原则: 内容优先、零运行时、Islands 按需交互
```

**一句话总结**：服务器 1.8G 内存养不起任何 Node 运行时，Astro 构建出纯 HTML 让 Nginx 直出 — 这是资源约束下唯一正确且优雅的解法。
