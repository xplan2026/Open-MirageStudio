> **分析对象**: Mirage-Studio 全项目（docs/standard/ 设计文档 + 各 Agent 模块 + 部署现状）

## 一、设计意图总览

### 1.1 顶层定位

**Mirage-Studio 是一个独立自媒体 IP 工作室**，以长篇连载小说《幻觉》为基石，通过多个 AI Agent 协作，持续生产跨媒介内容（小说、歌曲、MV、族谱可视化），并通过官方网站对外展示。

**核心理念**: 《幻觉》小说是骨架——它不一定要"完成"，而是在持续创作中变得越来越生动。补充信息越多，可供其他 Agent 创作的知识越丰富，工作室才有可持续生产的能力。

### 1.2 架构设计（SSOT v2.0，2026-08-09）

```
        │
        ▼

└──────┬───────────────┘
       │
       ├──────────────► Xujie Writer Agent ────► 《幻觉》小说章节
       │                      │
       │                      ▼
       │               Zhupu Manager Agent ──► 角色族谱数据
       │
       ├──────────────► Lemong Agent ────────► 歌曲 MP3
       │                      │
       │                      ▼
       │               Erhu Agent ───────────► 数字人 MV
       │
       └──────────────► 产物索引 → Website 展示
```

### 1.4 关键设计约束

1. **非自动联动**：小说更新不自动触发歌曲/MV 创作，所有下游创作需用户明确指令
2. **小说是基石但不是瓶颈**：即便小说未更新，也可基于已有内容独立创作歌曲和 MV
3. **用户始终在回路中**：每个创作环节都需要用户确认或发起
4. **人控 AI 辅助**：Agent 在 WebIDE 中手动运行，产出物保存到项目 `data/` 目录

## 二、执行逻辑分析

### 2.1 创作工作流（设计）

```
小说创作流:  用户指令 → Coordinator → Xujie Writer: 续写下一章
                                    → 新角色 → Zhupu Manager: 更新族谱
小说到歌曲流: 用户指令 → Coordinator → Lemong: 基于第X章主题创作歌曲
                                    → 产物路径回写
歌曲到MV流:   用户指令 → Coordinator → Erhu: 将歌曲《XXX》升级为 MV
                                    → MV 文件路径回写
```

### 2.2 数据流（设计 SSOT）

```
Agent 手动运行 → 产出到 data/ → git add/commit/push
    → GitHub (xplan2026/mirage-studio) [代码 + data/ 单一信任源]
    → 服务器端: git pull origin main → npm run build
    → 扫描 data/ → 生成页面 → Nginx serve dist/
```

**设计核心决策**：用 GitHub 做中间桥（WebIDE↔服务器无直连），GitHub 是 data/ 和源码的 SSOT，支持版本回溯，便于 CI/CD。

### 2.3 实际执行逻辑（与设计的偏差）

| 环节 | 设计 | 实际（实测） | 偏差评价 |
|------|------|--------------|----------|
| 代码仓库 | GitHub 单一信任源 | GitHub + CNB 双仓库双推 | 功能增强，但 CI 只在 GitHub 触发 |
| 官网部署 | 服务器 git pull + build + Nginx | GitHub Actions → Cloudflare Pages（CDN） | ✅ 更优（零服务器成本） |
| 媒体文件 | 构建时复制到 dist | CF Pages `_redirects` 代理回源服务器 `/data/` | ⚠️ 实测代理失效（见部署报告） |
| 工作台/后端 | —（SSOT 未定） | 腾讯云 4C4G + Nginx + PM2（coordinator:3100, ambassador:3200） | ✅ 合理 |
| 服务器更新 | git pull | 手动 scp/tar（无 git） | ⚠️ 有版本回溯缺失风险 |
| 生产调度 | Coordinator 调度 4 个生产 Agent（CLI 适配器） | 4 个 Agent **均未部署** + 适配器相对路径错误 + executeTask **模拟执行**（真实调用被注释） | ❌ 调度链路断裂，Coordinator 实际"光杆司令"（详见 §三 P0-1） |

## 三、设计缺失与技术债务备注

以下按严重程度排序：

### 🔴 P0 — 阻断性设计缺失

1. **4 个生产 Agent 均未部署，Coordinator 无法调度生产（光杆司令）** 🆕 2026-08-15 审计发现
   - **现象**：服务器 `/opt/mirage-studio/` 仅部署 `coordinator-agent` + `ambassador-agent`，`xujie-writer-agent/`、`zhupu-manager-agent/`、`lemong-agent/`、`erhu-agent/` 全部缺失（`data/` 数据在、Agent 程序不在）
   - **三层断裂**：
     - ① **Agent 代码未部署**：`deploy.sh` 只打包 coordinator-agent 自身，从不涉及 4 个生产 Agent
     - ② **适配器相对路径错误**：`lemong/erhu/zhupu` 三适配器调用 `node lemong-agent/lemong-agent`（相对路径），而 PM2 `cwd` 为 `/opt/mirage-studio/coordinator-agent` → 实际解析路径是 `/opt/mirage-studio/coordinator-agent/lemong-agent/...`，**即使 Agent 部署也 ENOENT**
     - ③ **executeTask 模拟执行**：`coordinator.js` 中真实适配器调用被注释（`TODO: Phase 3 替换为实际适配器调用`），任务直接标记"模拟成功"
   - **附带缺失**：`xujie-adapter.js` 从未创建（adapters/ 仅 3 个）；且 Xujie 是**人控对话式 Agent**（无 CLI 入口，依赖 IDE 工作流），本质不适合无头部署，调度模式未定义
   - **影响**：用户从工作台/微信下发创作指令 → Coordinator 标记"成功（模拟）"→ **实际零生产**。当前部署的仅是"意图解析 + 任务状态机"空壳
   - **专项计划**：见根目录 `TODO-调度链路.md`

2. **运行时产物与技术债务未分类（用户已确认）**
   - `data/` 混合了**运行时数据**（小说章节、歌曲、族谱等创作产物）与**运行时依赖/临时文件**，未分类
   - 前端技术选型中设计"媒体文件阶段一复制 dist、阶段二迁移 R2"，但**阶段二从未规划落地**，MP3/MP4 大文件全量进入 git 仓库与构建产物
   - **影响**：仓库膨胀、构建变慢、服务器磁盘压力、git 历史携带大文件

3. **服务器部署无版本管理**
   - 设计依赖 `git pull origin main` 更新服务器，实际服务器 `/opt/mirage-studio` **不是 git 仓库**，靠 deploy.sh 手动打包 scp
   - **影响**：无法回溯服务器版本、无法 diff 本地/服务器差异、内容丢失后无法恢复（正是本次"webIDE 内容丢失"事故的根源之一）

### 🟡 P1 — 功能性缺失

3. **微信 iLink-bot 待对接**：设计中最重要的用户入口（微信）仍为 🔴 待对接状态，当前实际入口仅 Admin-UI + CLI

4. **Admin-UI 未达"工作台"定位**：SSOT 规划的创作指令中心、产物管理中心、AI 推广交互均未实现；当前仅 v0.1 Dashboard + 任务编排

5. **Ambassador 对外暴露不完整**：A2A 协议接口在 Nginx 反代中指向 coordinator:3100 的 `/a2a/`，Ambassador:3200 自身未被 Nginx 配置反代（需要核实是否通过其他路径暴露）

6. **本地/服务器技术债目录混杂**：服务器存在 `static-workbench/workbench.bak*`、`.env.bak.20260812` 等历史备份；本地也存在多处重复/遗留目录（如 website 的 data symlink 设计未按文档实现）

### 🟢 P2 — 规范性缺失

7. **设计文档与代码漂移**：`前端技术选型.md` 称服务器为"阿里云 ECS 1.8G"，实际为腾讯云 4C4G；"部署=服务器 Nginx"实际为 CF Pages + 服务器双轨。文档需更新

8. **data/ 目录结构命名不一致**：`Lemong-data`、`XujieWriter-data` 等混用驼峰与连字符，各 Agent 数据目录规范不统一

## 四、结论

1. **设计意图清晰且自洽**：以《幻觉》小说为基石的多 Agent 协作工作室，Coordinator 统一调度、用户始终在回路中、GitHub 作为 SSOT 桥接 WebIDE 与服务器——这套设计在资源受限（1.8G 服务器）下是合理的
2. **实际架构基本遵循设计**：官网部署已从"Nginx 直出"升级为"CF Pages CDN"（更优），工作台合理采用"服务器 + Nginx + PM2"承载有状态后端
3. **主要缺口集中在四处**：
   - **生产调度链路断裂（P0-1，光杆司令）**：4 个生产 Agent 未部署 + 适配器路径错误 + executeTask 模拟执行，Coordinator 无法真正驱动任何生产 Agent（专项计划：`TODO-调度链路.md`）
   - 运行时产物/技术债务未分类（P0，用户已确认待处理）
   - 服务器非 git 仓库导致无版本管理与回溯（P0，事故根因）
   - 微信入口（iLink-bot）与工作台升级未完成（P1）

> 详细部署方式评估见《2026-08-15-部署方式评估报告》。
