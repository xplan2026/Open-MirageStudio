## 三、部署方案 vs 设计需求评估

### 3.1 官网部署 — 满足设计，且更优

| 设计（前端技术选型） | 实际 | 评估 |
|----------------------|------|------|
| 服务器 git pull + build + Nginx | GitHub Actions → Cloudflare Pages CDN | ✅ **更优**：零服务器成本、CDN 加速、CI 自动化 |
| 媒体复制进 dist | CF Pages `_redirects` 回源服务器 | ⚠️ **方案可行但当前失效**（见 §4.1） |

### 3.2 工作台部署 — 满足设计需求，合理

| 需求 | 实际 | 评估 |
|------|------|------|
| SPA 需后端 API | React SPA + Coordinator (3100) 同服务器 | ✅ 正确（SPA 不能纯 CDN） |
| 未备案域名被腾讯云拦截 | 灰云 DNS-only + 5656 端口 + DNS-01 SSL | ✅ 合理变通 |
| 登录认证 | `/auth/` QR 扫码 + JWT | ✅ 已修复 |

### 3.3 服务器更新机制 — 偏离设计（P0 问题）

| 设计 | 实际 | 风险 |
|------|------|------|
| 服务器 `git pull origin main`（有版本回溯） | 手动 scp/tar 覆盖（无 git） | 🔴 无法回溯、无法 diff、内容丢失不可恢复 |

## 四、发现的问题（按严重程度）

### 🔴 P0 — 官网媒体代理实际失效

**现象**：`https://mirage.cc.cd/data/Lemong-data/醉太平_渔利/醉太平_渔利.mp3` 返回 HTTP 200，但内容为 4946 字节 HTML（CF Pages 404 页），**不是 mp3 文件**；而同路径直连服务器 `http://182.254.180.26/data/...` 返回真实 3.3MB 文件。

**根因分析**（需进一步验证）：
- CF Pages `_redirects` 的 `200` 状态码规则是"服务端代理"，但 CF Pages 实际对 `200` 的支持可能未按预期回源；或回源请求被腾讯云对未备案域名的 80 端口拦截（服务器 80 直连外网测试本身返回 403/被拦）
- 之前 08-09 部署记录中的 `_redirects` 规则 `/data/* http://182.254.180.26/data/:splat 200` 依赖服务器 80 端口对外可达，但腾讯云 DPI 拦截 80/443 是已知问题（5656 端口就是为绕开它而设）——**回源端口 80 恰恰是被拦截的端口**，自相矛盾

**影响**：官网所有音乐/MV 媒体加载失败 → 官网"歌曲/MV"板块实际不可用

**建议**：
1. 将 `_redirects` 回源地址改为 `https://a-o-c.cc.cd:5656`（已验证可达）或新增 80 端口放行
2. 或按设计原案将媒体文件构建时复制进 `website/dist/assets/media/`（需解决大文件仓库膨胀）
3. 长期：按《前端技术选型》阶段二迁移 Cloudflare R2 + CDN

### 🟡 P1 — 服务器无 git、无自动化部署

- 全部内容靠 `deploy.sh` 手动打包 scp，无版本记录 → 与"GitHub 是 SSOT"的设计脱节
- 08-12 webIDE 内容丢失后无法从服务器 git 回溯，直接导致本次"双方不一致"排查成本上升
- **建议**：将服务器目录初始化为 git 仓库（或至少保留部署快照 tar 归档）

### 🟡 P1 — 媒体回源端口矛盾（承接 P0）

服务器 80/443 被腾讯云 DPI 拦截（部署记录明确记载），但媒体回源仍走 80 端口 → 链路必然不通。需统一走 5656 或 HTTPS。

### 🟢 P2 — Nginx 双站点配置重叠

`sites-enabled/` 同时启用 `coordinator` 与 `mirage-studio` 两份配置，职责边界不清（`coordinator` 站点 root 指向 `coordinator-agent/admin-ui/dist`，而 `mirage-studio` 站点 root 指向 `static-workbench`），存在路由/证书配置重复风险。建议合并为单一站点文件。

### 🟢 P2 — Ambassador 未纳入 Nginx 反代

Ambassador (3200) 已运行但 Nginx 仅反代了 coordinator 的 `/a2a/`（→3100）。Ambassador 的对外 A2A 能力是否暴露未在部署记录中体现，需核实并补充配置。

### 🟢 P2 — 服务器遗留技术债目录

`static-workbench/workbench.bak*`、`.env.bak.20260812`、admin-ui 新旧组件并存等，占用磁盘且无管理。建议清理或归档（本次对比中已识别，属"运行时产物未分类"的一部分）。

## 五、部署方式正确性结论

| 维度 | 结论 |
|------|------|
| 官网（静态） | ✅ **正确**，CF Pages + CI 优于原设计，唯一缺陷是媒体代理链路失效 |
| 工作台（有状态） | ✅ **正确**，服务器 + Nginx + PM2 + 5656 端口绕拦是合理方案 |
| 更新/回溯机制 | ❌ **偏离设计**，无 git 无 CI，是本次事故的根源 |
| 媒体链路 | ❌ **实际失效**，需修复（端口矛盾） |
| 整体 | 🟡 **方向正确，实现有 1 处致命缺陷（媒体代理）+ 1 处机制缺失（无版本管理）** |
