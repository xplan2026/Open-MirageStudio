## 二、与 Website 部署的对比

| 维度 | Website (mirage.cc.cd) | Admin-UI (a-o-c.cc.cd) |
|------|----------------------|------------------------|
| 框架 | Astro SSG | React SPA (Vite) |
| 输出 | 纯静态 HTML | 静态 JS bundle + 动态 API 调用 |
| CI/CD | ✅ GitHub Actions → Cloudflare Pages | ❌ 无 CI, 手动本地构建 + scp |
| 部署目标 | Cloudflare Pages CDN | 4C4G 服务器 Nginx |
| DNS | 橙云 (proxied) | 灰云 (DNS-only) |
| SSL | Cloudflare 自动 | Let's Encrypt DNS-01 |
| 后端依赖 | 无 | Coordinator API (localhost:3100) |

**关键差异**: Admin-UI 是 SPA，需要后端 API。所以不能像 Website 一样纯静态 CDN 部署，必须与 Coordinator 后端同服务器部署。

> **部署约束（2026-08-19 确认）**: Admin-UI 前端保持**手动部署、不使用 CI**（既定决策，见 `admin-UI部署方案.md` §4.1）。CI 仅部署后端代码，`deploy-server.yml` 的 rsync 明确排除 `admin-ui/dist/`。

## 三、Nginx 路由架构

```
a-o-c.cc.cd (HTTPS 443 + 5656)
├── /            → 301 → /workbench/
├── /workbench/  → static-workbench/workbench/ (SPA)
├── /admin/*     → proxy_pass localhost:3100 (Coordinator API)
├── /a2a/*       → proxy_pass localhost:3100 (A2A 接口)
└── /health      → proxy_pass localhost:3100

兜底 (HTTP 80, server_name _)
├── /            → website/dist/ (官网兜底)
├── /workbench/  → static-workbench/workbench/ (IP 访问可用)
├── /data/       → alias /opt/mirage-studio/data/ (媒体文件)
├── /admin/*     → proxy_pass localhost:3100
└── /a2a/*       → proxy_pass localhost:3100
```

### 为什么用 DNS-only (灰云) 而非 proxied (橙云)?

- 腾讯云对未备案域名进行 HTTP 请求拦截
- Cloudflare proxied 模式下流量经 CF 到腾讯云，会被拦截
- DNS-only 模式直接解析到服务器 IP，配合 Let's Encrypt HTTPS

### 为什么增加 5656 端口? (2026-08-11 补充修复)

即使是 HTTPS + DNS-only，443 端口仍可能被腾讯云网络层面的 DPI 拦截（手机/微信浏览器等外部网络不通，但腾讯云网内正常）。

**解决方案**: Nginx 同时监听 5656 端口（非标准 Web 端口），绕过腾讯云对 80/443 的深度包检测：

```nginx
server {
    listen 443 ssl;
    listen 5656 ssl;     # 新增 — 绕过腾讯云端口拦截
    server_name a-o-c.cc.cd;
    # ... SSL cert 复用 443 的配置 ...
}
```

**访问**: `https://a-o-c.cc.cd:5656/` — 手机/微信/桌面浏览器均可正常访问。

**前提**: 腾讯云安全组开放 TCP:5656 入站规则（来源 0.0.0.0/0）。

### Nginx /auth/ 路由 (2026-08-11 修复)

登录页为 QR 码扫码模式，前端调用 `/auth/qrcode` 和 `/auth/status`。Nginx 必须配置代理规则：

```nginx
# ==================== 认证路由 (QR 码扫码登录) ====================
location /auth/ {
    proxy_pass http://127.0.0.1:3100/auth/;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

> 2026-08-11 首次部署时遗漏此规则，导致登录页无法加载二维码。已修复并加入配置。

## 四、API 配置

生产环境 API 使用相对路径 `/admin`，由 Nginx 代理到 Coordinator：

```js
// coordinator-agent/admin-ui/src/api.js
const API_BASE = '/admin';  // Nginx proxy_pass → localhost:3100
```

本地开发时，Vite dev server 自动代理：

```js
// vite.config.js
proxy: {
  '/admin': { target: 'http://localhost:3100', changeOrigin: true }
}
```

### Coordinator 环境变量 (.env)

服务器 `/opt/mirage-studio/.env` 关键配置：

| 变量 | 值 | 说明 |
|------|-----|------|
| `COORDINATOR_PUBLIC_URL` | `https://a-o-c.cc.cd:5656` | 微信扫码回调 URL，**必须用 5656 端口**（443 被腾讯云拦截） |
| `ADMIN_SECRET` | `YFREvYqNcDpc` | 扫码后输入此 12 位密钥完成登录 |

### 登录流程

```
用户打开 https://a-o-c.cc.cd:5656
  → 301 → /workbench/
  → SPA → /workbench/login
  → 前端 fetch('/auth/qrcode')  [Nginx proxy_pass → localhost:3100]
  → 显示微信二维码
  → 微信扫码 → 输入 ADMIN_SECRET → 获取 JWT → 跳转 Dashboard
```

## 六、网关功能规划

当前架构已支持基础网关功能：
- Nginx 反向代理 (`/admin/*` → Coordinator)
- Nginx 可扩展：限流、IP 白名单、Basic Auth 前置
- Coordinator 后端实现：JWT 认证、权限控制、WebSocket

未来如果需要更复杂的网关（如 API 版本路由、多服务编排），应在 **Coordinator 后端**实现，而非前端。当前静态部署方案完全适用。
